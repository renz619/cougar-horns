SUMMARY OF WHAT WENT WRONG

The core scripts exist, but they are not connected into a running application.
Passing classifier tests does not prove that headset joint data reaches them.
The open sample scene and the scene selected for builds are also different.
Android is not configured for XR, although the Windows/Quest Link setup is.

VERIFIED FINDINGS

1. The custom hand adapter is not attached to a saved scene or prefab.

   File: Assets/Scripts/HandPose/QuestHandAdapter.cs
   Namespace: HandPoseRecognition
   Component: QuestHandAdapter
   Output property: currentHand (HandJointData)
   Default hand: Right; selectable through the serialized handedness field.

   Its script GUID is 9d30f4aa0f724475694ac457235757bd. A search found no
   reference to that GUID in saved .unity or .prefab files under Assets.
   As a MonoBehaviour, the adapter needs an active scene GameObject to run.
   Merely having its .cs file in Assets does not start hand reading.

2. There is no runtime connection from hand data to classification and text.

   File: Assets/Scripts/HandPose/HandPoseClassifier.cs
   API: HandPoseClassifier.Classify(in HandJointData hand,
                                  HandPoseClassifierSettings settings)

   The only calls to Classify found under Assets are in EditMode tests.
   No runtime component consumes QuestHandAdapter.currentHand.
   The required HandPoseDisplay.cs does not exist.
   Consequently, the application has no implemented OPEN/FIST/UNKNOWN feedback.

3. The configured build scene is the starter scene.

   File: ProjectSettings/EditorBuildSettings.asset
   The only enabled build scene is Assets/Scenes/SampleScene.unity.
   That scene contains the starter camera, light, and volume, without the
   custom adapter or pose display. Its camera has no tracked-pose driver.

   During review, the Editor had this different scene open:
   Assets/Samples/XR Hands/1.5.1/HandVisualizer/HandVisualizer.unity

   The sample includes an XR Origin and sample visualization components, but
   it is not included in the build list and does not run the custom classifier.
   Opening or testing this sample does not configure the application build.

4. Android standalone deployment is not configured for hand tracking.

   File: Assets/XR/XRGeneralSettingsPerBuildTarget.asset
   The Android Providers object has m_Loaders: [].

   File: Assets/XR/Settings/OpenXR Package Settings.asset
   HandTracking Android is disabled (m_enabled: 0).
   MetaQuestFeature Android is disabled (m_enabled: 0).

   Windows/Standalone has an OpenXR loader and Hand Tracking Subsystem enabled.
   Android changes are necessary for an APK running directly on Quest, but
   they do not fix a Windows Editor/Quest Link scene-wiring problem.

IMPLEMENTATION PLAN

1. Preserve existing work and keep the core architecture.

   Review git status before editing. At review time, this file already had
   uncommitted user changes:
   Assets/XR/Settings/OpenXR Package Settings.asset
   Preserve those changes rather than overwriting the asset wholesale.
   The review made no source changes.

   Keep HandJointData.cs, HandPose.cs, HandPoseClassifier.cs, and
   HandPoseClassifierSettings.cs unless evidence requires a specific correction.
   Defaults are extended <= 60 degrees and curled >= 160 degrees of total
   finger bend. Do not change them merely because the pipeline is disconnected.

2. Implement a small HandPoseDisplay MonoBehaviour.

   Put it under Assets/Scripts/HandPose in namespace HandPoseRecognition.
   Serialize references to QuestHandAdapter and a TextMeshPro TMP_Text target.
   Serialize an initialized HandPoseClassifierSettings instance so thresholds
   can be tuned in the Inspector.

   In Update, read adapter.currentHand and call the existing classifier.
   Map HandPose.Open to OPEN, Fist to FIST, and Unknown to UNKNOWN.
   Force a correct initial label, then update text only when the result changes.
   An unavailable/disabled adapter or invalid tracking must produce UNKNOWN.
   Handle missing Inspector references without repeated NullReferenceExceptions;
   provide a clear setup error rather than flooding the Console.

   Assets/Scripts/HandPose/HandPose.Runtime.asmdef currently references XR Hands
   only. If the display is in this assembly, add the installed TextMeshPro
   assembly reference. Its actual definition is available at:
   Library/PackageCache/com.unity.ugui/Runtime/TMP/Unity.TextMeshPro.asmdef
   Verify assembly names/GUIDs locally rather than inventing them.
   TextMeshPro is provided by the installed UGUI package; do not upgrade packages
   or add a duplicate legacy TMP package just to implement the label.

3. Create and wire an application scene.

   A reasonable new path is Assets/Scenes/HandPoseDemo.unity.
   Use the installed HandVisualizer sample as a reference for compatible XR
   Origin, camera, and tracked-pose-driver setup. Keep application changes in
   the application's own scene rather than modifying PackageCache source.

   Create an active GameObject named Hand Pose Recognition.
   Add QuestHandAdapter and select Right initially.
   Add HandPoseDisplay and assign the adapter reference.
   Add a readable TextMeshPro label on a world-space Canvas positioned in front
   of the tracked camera; assign it to HandPoseDisplay.
   Import TMP essential resources if needed and verify visibility in the headset.
   Optional sample hand meshes are not required for pose classification.

   Save the scene and include it as the startup scene in Build Settings/Build
   Profiles. Ensure the intended build uses it instead of the untouched starter
   scene. Preserve Unity .meta files and valid script/asset GUID references.

4. Validate the intended platform.

   First validate Windows Editor/Quest Link, which is the current project
   workflow described in CLAUDE.md. Confirm OpenXR initialization and Hand
   Tracking Subsystem for Standalone. Keep working existing settings.

   If a native Quest APK is part of the implementation scope, separately enable
   the Android OpenXR loader, Hand Tracking Subsystem, and applicable Meta Quest
   support. Resolve Project Validation issues using the installed packages and
   current official platform guidance. Do not conflate Android and Standalone
   settings or assume optional aim/controller profiles are required for raw
   finger-joint reading.

5. Verify compilation, behavior, and real hardware.

   Run the existing 10 EditMode tests again and resolve compilation errors.
   Add focused tests only where new behavior needs coverage, such as initial
   UNKNOWN text or tracking-loss feedback. Do not replace headset verification
   with additional synthetic classifier tests.

   For a physical test, connect Quest Link, enable headset hand tracking, wear
   the headset, and keep the selected hand visible to its cameras. Confirm a
   running XRHandSubsystem, currentHand.isTracked, and valid index/middle/ring/
   little joints. Brief temporary diagnostics can expose these values; avoid
   per-frame log spam and remove temporary instrumentation after verification.

   Acceptance checks:
   - Open all four fingers: display OPEN.
   - Curl all four fingers into a fist: display FIST.
   - Mixed or intermediate pose: display UNKNOWN.
   - Move the hand out of tracking or stop tracking: display UNKNOWN rather than
     retaining the previous pose.
   - Disable the adapter or stop XR: display UNKNOWN without exceptions.
   - Rotate and translate the hand: recognition remains consistent.
   - Restart Play mode/application: initialization recovers correctly.
   - If delivering an APK, repeat these checks on the built application.

   Tune thresholds only after observing real joint curls. If hardware is
   unavailable, explicitly mark live tracking and the hardware acceptance
   checks as unverified rather than claiming completion from synthetic tests.
